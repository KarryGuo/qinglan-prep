# 青蓝备课 项目说明书

版本 v0.2 · 2026-08-16 · 编码实现的唯一需求来源（v0.2 变更：数据库由 Neon Postgres 更换为 Turso）

本文档定义青蓝备课的产品行为与工程规格。技术选型与架构见《技术架构方案.md》，两文档冲突时以本文档的产品行为为准、以架构文档的技术决策为准。

## 1. 产品概述

青蓝备课是一个从学情诊断开始的备课 Agent，口号"让每一节课，都有备而来"。教师输入一个课题和班级情况，系统先给出学情画像，再对齐课标完成教学设计，生成教案、课件大纲、板书、分层作业与随堂测，每个设计点都能点开看依据；课后录入作业结果，系统复盘并更新班级学情记忆，下一次备课自动更准。

目标用户是中小学教师，尤其是青年教师与缺少教研支持的县域乡村教师。产品对教师的价值是一天省出两小时、备课有依据；对评委的价值是一条可观察、可追溯、带记忆的 Agent 任务闭环。

## 3. 页面与交互规格

### 3.1 落地页 /

顶部一句话定位与口号，中部用四张卡片讲"诊—设—生—思"，下部两个入口按钮："开始一节示范课"（跳转到以《荷花》预填的新建表单）与"查看 Agent 工作过程"（跳转到示范课的 trace 页）。页脚固定合规声明。验收：首屏 2 秒内可见主文案；两个入口均可达。

### 3.2 新建备课 /prep/new

表单字段：学科（一期固定"语文"）、年级（三/四年级）、教材版本（固定"统编版"）、课题（下拉，来自 TextbookNode，含《荷花》等 8 个节点）、班级学情描述（多行文本，预填示范文案）、班级（默认"三年级 2 班"）。提交后创建 Lesson 并跳转 /prep/[id]。验收：空课题提交被拦截并提示；创建成功后 status 为 diagnose。

### 3.3 备课流程 /prep/[id]

页面左侧为四阶段步骤条，右侧为当前阶段工作区。工作区顶部是输入摘要卡（课题 + 学情描述 + 班级记忆摘要），中部是流式事件流（思考、工具调用、工具返回以折叠卡片实时出现），底部是阶段产物卡与两个按钮："确认并进入下一步""提出修改"（修改意见文本框）。

阶段推进规则：diagnose 确认后 status 变 design；design 确认后变 generate；generate 确认后变 delivered 并出现"查看备课包""录入课后结果"两个出口。任何阶段收到 confirm_required 事件时，工作区显示模型提出的补充问题，教师回答后自动重跑本阶段。

异常态：error 事件显示"本阶段执行失败，请重试"与重试按钮；连续两次失败提示联系信息。验收：四个阶段可连续走完；中途刷新页面能恢复到当前 status 对应阶段，历史事件从 RunEvent 回放。

### 3.4 备课包 /prep/[id]/package

标签页：教案 / 课件 / 板书 / 分层作业 / 随堂测。教案以结构化文档呈现（目标、重难点、环节表、设计意图）。每个目标、环节、题目右侧有引用角标 [课标][教材][学情]，点击在右侧溯源面板展开 Citation 列表（类型、人读引用、原文片段）。右上角"导出 Markdown"调用 export 接口下载。页脚固定"供备课参考"声明。验收：示范课的备课包至少包含 2 条课标引用、1 条教材引用、1 条学情引用，且角标均可点开。

### 3.5 课后反思 /prep/[id]/reflect

输入区：随堂测各题正确率（默认用 generate 产出的 quiz，教师填百分比），支持三种录入方式——手工填写、上传成绩 CSV（表头含"题号""正确率"两列，前端解析自动回填）、拍照/上传成绩单照片（前端压缩至最长边 1600px 后调用 `/api/lessons/[id]/reflect/ocr`，由视觉模型 VLM_MODEL 识别题号与正确率回填，识别结果教师核对后提交）。提交后流式执行 reflect 阶段，产出复盘报告卡（总体判断、逐知识点对比"预测 vs 实际"、下一课建议）与记忆更新摘要（哪些弱点已解决、哪些新增）。完成后 status 变 reflected，/class 页同步更新。验收：反思完成后 ClassMemory.profile 的 updatedAt 变化且弱点了表有增量；照片识别接口带课程归属校验（非属主 403），图片超限（>5MB 或非 png/jpg/webp）返回 400。

### 3.6 学情记忆 /class

展示班级画像：弱点了表（名称、严重度星号、最近证据、更新时间）、已解决弱点、历史课列表（课题 + 日期 + 反思摘要链接）。验收：完成一次完整闭环后，本页能看到《荷花》带来的记忆变化。

### 3.7 Agent 过程 /prep/[id]/trace

按时间线展示 RunEvent：阶段分隔、思考文本、工具调用（名称 + 参数）、工具返回（JSON 折叠）、校验与定稿。顶部统计条：工具调用次数、总耗时、引用条数。这一页是答辩主战场，要求视觉清晰、无需解释即可看懂。

## 4. Agent 行为规格

四个阶段的输出类型（TypeScript 表示，编排层用 zod 做运行时校验）：

```ts
type DiagnoseOutput = {
  summary: string;
  prerequisites: { name: string; mastery: "solid" | "average" | "weak"; basis: string }[];
  weakPoints: { name: string; severity: 1 | 2 | 3; evidence: string; suggestion: string }[];
  attentionNote?: string;
  questionsForTeacher?: string[];   // 非空时触发 confirm_required
};

type DesignOutput = {
  keyPoints: string;
  difficultPoints: string;
  objectives: { text: string; curriculumRef: string }[];      // curriculumRef 必须来自 search_curriculum 返回的 code
  stages: {
    name: string; minutes: number;
    teacherActivity: string; studentActivity: string; intent: string;
    citations: { type: "curriculum" | "textbook" | "classdata"; ref: string }[];
  }[];
  boardDesign: string;
};

type GenerateOutput = {
  planMarkdown: string;
  slides: { pageTitle: string; bullets: string[] }[];         // 10-14 页
  board: string;
  homework: { tier: "basic" | "advanced" | "extension";
              items: { text: string; answer: string; knowledgePoint: string }[] }[];
  quiz: { text: string; answer: string; knowledgePoint: string }[];  // 5 题
};

type ReflectOutput = {
  overall: string;
  perKnowledgePoint: { name: string; predicted: string; actual: string; delta: string }[];
  nextLessonSuggestions: string[];
  memoryPatch: { resolved: string[];
                 newWeakPoints: { name: string; severity: 1 | 2 | 3; evidence: string }[] };
};
```

行为约束：

1. diagnose 必须先调用 read_class_memory 与 search_textbook 再下结论；weakPoints 数量 2-4，每条 evidence 必须引用记忆或教材节点内容。
2. design 的每个 objective 的 curriculumRef 必须是工具返回的真实 code，禁止自拟；校验层对引用做存在性检查，不存在则纠正轮报错。
3. generate 的 quiz 与 homework 优先取 search_questions 返回的题目，允许改写但 knowledgePoint 必须继承；分层作业三档各不少于 2 题。
4. reflect 的 memoryPatch.resolved 只能来自当前记忆中的弱点名称；write_class_memory 由编排层在 stage_done 后执行，不让模型直接改库。

## 5. 提示词模板规格

模板存于 src/agent/prompts.ts，变量用双花括号。四个阶段共享的系统前缀：

```
你是"青蓝备课"的{{stage_name}}智能体，服务于中小学语文教师的备课工作。
工作原则：
1. 先查证后结论：涉及课标、教材、学情的判断，必须先调用工具获取依据，再输出。
2. 不直接给学生答案类产品，不评价具体学生，只面向教师提供教学建议。
3. 信息不足时提出补充问题，而不是猜测。
4. 输出严格遵循给定 JSON Schema，不输出 Schema 之外的字段。
5. 所有教学建议附依据引用；无依据的判断标注 confidence: low。
最终产物页脚将由系统附加"供备课参考，教学决策由教师作出"，你无需重复。
```

diagnose 阶段用户提示词骨架：

```
课题：{{subject}} {{grade}} {{textbook}} 《{{title}}》
教师学情描述：{{classDesc}}
请完成学情诊断：先读取班级记忆与教材节点，输出 DiagnoseOutput。
若教师描述与班级记忆冲突，以记忆为基线、在 summary 中说明差异。
```

design 阶段追加注入 diagnose 产物，并要求"针对 weakPoints 中 severity≥2 的每一项，至少设计一个教学环节予以回应，并在该环节 citations 中标注 classdata 引用"。

generate 阶段追加注入 design 产物，要求"作业与随堂测的知识点覆盖 weakPoints；三档难度比例约 5:3:2"。

reflect 阶段用户提示词注入 quiz 各题正确率与 diagnose 的预测，要求输出 ReflectOutput 且 memoryPatch 与报告自洽。

## 6. 种子数据规格

范围：语文，统编版。数量下限：课标条目 67 条（覆盖第一、二、三学段，即 1-2 年级、3-4 年级、5-6 年级的识字与写字、阅读与鉴赏、表达与交流、梳理与探究条目节选整理）、教材节点 21 个（三上、三下、四上、四下四册，必含《荷花》《守株待兔》《赵州桥》《猫》）、题目 93 道（覆盖"段落大意概括""修辞辨认""关键语句理解""把握主要内容""体会思想感情""批注阅读""按顺序写景"等 15 个知识点，三档难度）、示范教师"王老师"、班级记忆"三年级 2 班"（弱点：段落大意概括 severity 3、注意力持续时间短 severity 2）。

种子 JSON 放 src/data/，seed.ts 读取后幂等写入。所有种子数据在 README 与 /class 页脚标注"演示用模拟数据，节选整理自公开课标文本"。

## 7. 非功能需求

- 性能：页面 SSR 首字节 ≤ 1.5s（热态）；阶段执行首事件 ≤ 5s。
- 冷启动：休眠唤醒时落地页显示"服务唤醒中，约半分钟"，不显示报错。
- 限流：/api/lessons/run 每 IP 10 次/分钟，超限返回 429 与友好提示。
- 可观测：RunEvent 全量留痕；/api/health 返回 {ok, uptime, dbOk}。
- 免责：备课包、导出文件、反思报告页脚固定声明文案。

## 8. 演示脚本

与参赛 PPT 第 11 页一致，端到端约 3 分钟：

1. 落地页点"开始一节示范课"，表单已预填《荷花》与学情描述，直接提交。
2. diagnose 流式运行：可见 read_class_memory、search_textbook 两次工具调用，产出学情画像（薄弱点：段落大意概括）。教师点确认。
3. design 运行：可见 search_curriculum 调用，产出目标与环节，环节"为段落大意搭建脚手架"带 classdata 引用。确认。
4. generate 运行：产出教案、12 页课件大纲、三档作业、5 题随堂测。打开备课包，点开 2 个引用角标展示溯源面板。
5. 进入反思页，填入正确率（概括题 68%，其余 80%+），运行 reflect，报告给出"41% → 68%"式对比与下一课建议，学情记忆页出现更新。
6. 打开 trace 页，回放全过程，展示工具调用次数与引用条数统计。

## 10. Render 部署步骤

1. 在 GitHub 创建公开仓库 qinglan-prep，推送含 render.yaml 的代码。
2. 在 Turso 控制台创建免费数据库（区域选离评委或自己近的，如 ap-east），复制 libSQL 地址与访问令牌。
3. Render 控制台 New → Blueprint，选择仓库，识别 render.yaml。
4. 填入环境变量 TURSO_DATABASE_URL、TURSO_AUTH_TOKEN、LLM_API_KEY、SESSION_SECRET（其余有默认值；千问密钥同时驱动文本模型 qwen-plus 与视觉模型 qwen-vl-plus，可用 VLM_MODEL 覆盖），创建。
5. 首次部署执行 db push 与 seed，访问 /api/health 确认 {ok:true}。
6. UptimeRobot 新建 HTTP 监控，每 10 分钟 ping /api/health。
7. 把在线地址写入 README 与参赛材料。
